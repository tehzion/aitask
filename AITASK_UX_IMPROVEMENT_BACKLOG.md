# AiTask UX Improvement Backlog

Backlog date: 2026-10-18 (MYT)  
Source: [AITASK_UX_AUDIT.md](./AITASK_UX_AUDIT.md) and [AITASK_WORKFLOW_EFFICIENCY_REPORT.md](./AITASK_WORKFLOW_EFFICIENCY_REPORT.md)  
Scope: UX/productivity improvements that preserve current business rules, permissions, client isolation, and the separate P0/P1 platform stabilization track.

## Prioritization rules

- **P0:** a current usability/release regression that blocks a verified workflow or weakens a safety boundary.
- **P1:** a daily productivity improvement supported by current evidence and implementable without changing business rules.
- **P2:** a valuable collaboration, administration, export, or information-architecture enhancement after the daily path is stable.
- **P3:** advanced personalization or command-surface work that should follow usage evidence.

Effort estimates are for one experienced engineer familiar with this repository, excluding security review, user research, production rollout, and external service configuration.

## P1 — daily productivity

| ID | Problem and evidence | Proposed solution and expected benefit | Dependencies / complexity | Security considerations | Acceptance criteria |
| --- | --- | --- | --- | --- | --- |
| UX-101 | Header search looks global but is route-scoped in `Navbar.tsx`; users cannot search all authorised tasks, projects, companies, clients, and service plans from one place. | Add a permission-scoped global result popover/page using existing visibility selectors and route builders. Keep the current route query as “filter this page” when the user is already on a searchable page. Benefit: fewer context switches and faster record retrieval. | Reuse `getVisibleTasks`, `getVisibleProjects`, client/service selectors, `CommandPalette`, and `useImeSafeInput`; medium; 4–7 days. No search service initially. | Never search raw unfiltered state in secure mode. If a server read model/RPC becomes necessary, apply workspace/company/client scope and negative tests. | Search by title/name/identifier returns only authorised records; each result shows type/context and deep-links correctly; `/` focuses search; mobile search is usable; empty/loading/error states are localized; no permissions are gained through search. |
| UX-102 | `CreateTaskModal.tsx` exposes task details, client/assets, assignment/timeline, links, and notes before the primary action. The existing happy path is only five interactions once a project exists, but the form requires scanning many optional controls. | Add a quick first view with title, project/company, assignee, deadline, and optional priority; place links, notes, visibility, service, and other advanced fields behind an explicit “More details” disclosure. Reuse contextual prefills and the same `addTask` validation. Benefit: faster routine creation without reducing capability. | Depends on UX-001 only for onboarding targets; medium; 3–5 days. | Keep `canCreateTasks`, assignment guards, company/project scope, client visibility, HTTPS validation, draft recovery, and idempotent save behavior unchanged. | Existing tests still pass; quick create cannot submit incomplete/unauthorised records; advanced values persist; contextual project/assignee prefills work; errors focus or link to the invalid field; mobile submit remains visible and safe. |
| UX-103 | Task filters and `viewType` are local React state. URL search/route filters survive a link, but department, status, priority, dates, and table/board preference reset after navigation. | Store a versioned per-user preference for preferred task view, sort, and selected saved filters. Provide role-relevant presets such as My overdue, Waiting approval, Department work, and Client deliveries. Benefit: less repeated filtering. | Reuse existing preference/localStorage patterns first; secure mode can later persist through an authorised user-preferences record; medium; 3–5 days. | Preferences are hints only; every query re-applies current visibility and role checks. Do not persist sensitive record data in URLs/localStorage beyond existing safe identifiers. | A user can save/rename/delete a filter; reopening `/tasks` restores the selected view; expired/unauthorised records simply disappear; presets are localized; saved filters never reveal another company. |
| UX-104 | Staff already have `StaffMyWork` buckets, while the platform backlog is adding an Action Centre. Without clear boundaries, another queue could duplicate dashboards and notifications. | Define My Work as personally assigned execution (`Needs action`, `Up next`, `Waiting`, `Done`) and Action Centre as decision/exception items. Align labels, empty states, and deep links; reuse `buildStaffWorkQueue`, notification categories, and platform Action Centre selectors. Benefit: users know where to execute versus decide. | Depends on the platform backlog’s Action Centre read model; medium; 3–5 days for UX alignment after its contract exists. | Each queue must use the actor’s existing visible/actionable selectors; client queue includes only client-visible review/delivery actions. | Staff sees assigned responsibilities in My Work; PM/HOD sees decision queues in Action Centre; notifications remain an event feed; no duplicate item appears in both without a clear reason; each item deep-links to the same record. |
| UX-105 | Save/retry/restore states are implemented across task, company, calendar, settings, and workspace surfaces, but users may see a local alert, toast, workspace banner, or draft notice with different wording. | Standardize operation-state copy and placement: Saving, Saved, Waiting for confirmation, Retry, Restored saved data, Rejected. Add field-linked validation and focusable summaries where a form has multiple errors. Benefit: users know what happened and what to do next. | Reuse `useSaveAction`, `BackendFreshness`, `actionFeedback`, `SystemMessage`, and `DraftRecoveryNotice`; medium; 3–5 days. | Do not expose raw backend/RLS details or hidden record names. Preserve live-region announcements, focus management, and retry/restore safety. | Failed operations never show success; every failed mutation states saved/unsaved status and next step; field errors are adjacent and announced; retry/restore actions are keyboard reachable; English/Chinese copy passes verification. |

| --- | --- | --- | --- | --- | --- |
| UX-201 | Task detail has a useful desktop split view and client-safe content, but the mobile view is one long scroll containing status, workflow guards, editing, delegation, files, review, comments, and history. | Improve hierarchy in the existing sheet: current decision/evidence first, requirements and assignment second, activity/history and comments afterward. Prefer anchored sections or a compact summary before introducing tabs. Benefit: reviewers find the next action faster. | Reuse `TaskDetailsModal`, `ClientDeliveryFocus`, `StaffTaskFocus`, and current permission gates; medium; 4–6 days. | Do not merge internal notes/comments/files into client projections. | UX-202 | Comments are supported, but no unread comment indicator or lightweight mention affordance was found. A complex messaging system would duplicate the current update model. | Add a simple unread-update marker tied to existing notification/read state, and optionally a constrained `@` suggestion list for visible members only. Benefit: reviewers see changed task context without opening every task. | Depends on notification/read model and unified activity projection; medium; 3–5 days for unread-only; high if mentions are added. | Member suggestions must be scope-limited; client-visible comments remain separate from internal comments; notifications need rate limits and deduplication. | Unread state is clear in My Work/Notifications/task detail; marking the task/activity read is idempotent; clients never see internal updates; no notification loop is introduced. |
| UX-203 | `/approvals` supports invitations, registrations, roles, departments, custom access, and member removal, but no clear resend/expiry lifecycle was found in the UI. | Add invitation status, expiry date, resend, and explicit active/deactivated labels only after a separate auth/security review. Benefit: administrators understand account state and recover invitations without destructive recreation. | Requires security review of `invite-aitask-member`, auth invitation state, registration history, and member deletion semantics; medium/high; 5–8 days. | Boss-only controls, server validation, RLS, invitation claim/idempotency, and audit history are mandatory. | UX-204 | Reports export useful CSVs, but export scope and available formats are not consistently discoverable across task, client, service, and approval surfaces. | Add an export summary showing scope, date range, included fields, and redaction rules. Benefit: exports become trustworthy business artifacts. | Reuse current report export utilities and client projection; medium; 3–5 days. | Server-enforce scope; clients receive only client-safe rows/fields; never export internal notes, assignees, departments, prices, or private URLs without permission. | Export filename and summary state selected scope/date; CSV content reconciles to visible rows; client exports exclude internal fields; empty exports are explicit; locale labels are correct. |
| UX-205 | Mobile route rendering passes no-overflow checks, but long forms, dense filters, and task cards still require repeated scrolling. | Run a focused tap-sequence audit for task creation, task detail, file upload, comment, approval, notification, and search at 320/375/390px after UX-001. Benefit: fewer mis-taps and less scroll hunting. | Depends on UX-001 and UX-102/201; low/medium; 2–4 days after interaction audit. | Preserve touch target sizes, focus traps, safe-area offsets, modal inertness, and client isolation. | No horizontal overflow; all primary actions are reachable; no overlay intercepts unrelated controls; touch targets meet project standards; keyboard and screen-reader checks remain green. |

## Recommended implementation order

1. Complete the existing stabilization-owned `UX-001` onboarding fix and rerun focused app smoke.
2. Implement `UX-101` global search as a read-only, permission-scoped surface using existing selectors.
3. Implement `UX-102` quick task creation and regression coverage.
4. Implement `UX-103` saved filters/view preferences and `UX-105` operation-state copy together where the same task surfaces are touched.
5. Align `UX-104` with the platform Action Centre backlog instead of creating duplicate queue logic.
6. Improve task detail hierarchy (`UX-201`) and then evaluate unread collaboration cues (`UX-202`).
7. Handle invitations/exports (`UX-203`, `UX-204`) only after security/data-contract review.
8. Run the focused mobile tap audit (`UX-205`) after the above surfaces settle; defer P3 work until usage evidence exists.
